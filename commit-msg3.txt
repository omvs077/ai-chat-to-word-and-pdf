Fix broken image references introduced by the previous DOCX format-mislabeling fix

Regression in 96a6001: that fix corrected each embedded image's file
extension by mutating ImageRun's .key/.imageData.fileName AFTER
construction. Confirmed via a real multi-image export (2 WEBP + 7 JPEG,
the same real conversation used to find the original bug) that this broke
EVERY image reference, not just non-PNG ones - Word showed "This image
cannot currently be displayed" for all of them.

Root cause: ImageRun's Drawing/Graphic tree (built inside the constructor)
bakes a placeholder "rId{<filename>}" directly into the XML using
imageData.fileName as it exists at that exact moment. A later
find-and-replace pass resolves that placeholder by matching against
whatever key Media.addImage() registers the file under during prepForXml().
Mutating .key/.imageData.fileName between those two moments desynced the
placeholder actually baked into the XML from what the later pass searched
for, leaving the raw, unresolved "rId{name.png}" string sitting in the
final document.xml for every image, regardless of format.

Fix: pass the real extension into ImageRun's constructor instead of
mutating after the fact - the vendored ImageRun class now accepts an
optional `extension` option (defaults to "png", so any other caller keeps
existing behavior), used when generating the initial `key` before Drawing
is ever built. docx-generator.js just passes it straight through. No
post-construction mutation anywhere.

Verified against:
  - A real multi-image, mixed-format synthetic document (webp+jpeg+png)
  - All 9 real images extracted from the actual broken export that
    surfaced this bug, reconstructed in the same multi-image arrangement
  - Confirmed via a real revert-and-rerun that the new regression test
    actually fails on the broken code (not just passes on the fix)

New regression test: 'every image reference in a multi-image, mixed-format
document resolves to a real relationship'. The existing single-image
WEBP/JPEG tests never caught this originally because they only checked
that files existed with the right name/content-type, never that r:embed
references actually resolve - both of those tests now also check
resolution, closing that gap.

Test suite: 30 -> 31 passing tests.
