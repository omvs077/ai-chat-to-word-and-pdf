Fix hard-coded "Claude" label and ChatGPT code-block escaping (from the first real ChatGPT export)

Both bugs found by generating and inspecting an actual ChatGPT export
end-to-end for the first time (extraction itself now works after the two
prior scroll-container fixes).

1. Assistant role label was hard-coded as literally "Claude" in both
   generators (lib/docx-generator.js, lib/pdf-generator.js), regardless of
   which adapter produced the IR - a genuine ChatGPT export still showed
   "Claude" as the label for every assistant turn. Both content scripts
   now set assistantName on the result object ('Claude' for content.js,
   'ChatGPT' for chatgpt-content.js), and both generators read
   ir.assistantName (defaulting to 'Claude' only when absent, so nothing
   changes for any other caller).

2. ChatGPT's code blocks were unreadable in the real export: literal
   "def binary\_search(arr, target):" as one of many separate plain
   paragraphs, all indentation lost. Root cause: chatgpt-content.js
   extracted clean code text into a separate `codeBlocks` array that nothing
   downstream ever consumed - the same class of gap Claude's t.images
   once had - while leaving the real CodeMirror structure (<pre
   class="cm-content"><code><span>...per-token spans...) untouched in the
   captured HTML. Turndown's default pre>code detection doesn't recognize
   that shape, so it fell through to treating everything as plain inline
   prose, backslash-escaping underscores/equals/brackets the way it would
   for any regular text containing those characters.

   Fix: normalizeCodeBlocks() now replaces each real <pre> in the CLONE
   with a clean <pre><code>text</code></pre> Turndown's own default
   handling already recognizes correctly (matching how Claude's plain code
   blocks work, no separate array needed - removed the now-dead
   `codeBlocks` field entirely). Text is read from the LIVE <pre> elements
   via .innerText before cloning, not from the clone itself - a cloned,
   detached node has no layout in a real browser, so .innerText on it
   would be unreliable.

   Verified end-to-end: normalized HTML confirmed clean, then run through
   the real vendored Turndown library directly, confirming a genuine
   ```-fenced code block with no escaping - not just an intermediate HTML
   shape check.

  - Three links (Python Documentation / MDN Web Docs / freeCodeCamp,
