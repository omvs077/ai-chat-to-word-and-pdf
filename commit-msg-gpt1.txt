Add ChatGPT adapter v1: text, headings, lists, links, code blocks

New content/chatgpt-content.js, wired into popup.js's existing platform
detection (extended to also recognize chatgpt.com) and content-script
injection (picks the right file per platform - manifest.json needed zero
changes, since there's no content_scripts/host_permissions declared at
all; everything already injects on-demand via activeTab+scripting). The
markdown-assembly pipeline in popup.js and both document generators are
already fully platform-agnostic and needed no changes to consume this
adapter's output.

All selectors below were confirmed via live DevTools inspection of a real
ChatGPT conversation (never guessed):
  - [data-message-author-role="user"|"assistant"] - real, authoritative
    turn-role selector; simpler than Claude's situation since one
    attribute covers both roles instead of two separate selector sets.
  - data-testid="conversation-turn-N" carries the real turn index directly
    in the attribute value (confirmed: turns 10, 11, 14, 18-22 mounted
    simultaneously during virtualization) - ordering is a direct regex
    parse, no ancestor-walk/hop-count needed the way Claude's data-index
    required.
  - The scroll container is found via content.js's existing
    findScrollContainer() unchanged - it was already a generic "walk up
    until something actually scrolls" check, not Claude-specific, so it
    finds ChatGPT's real scrollport-classed container without needing that
    class name hardcoded anywhere.
  - Code blocks are CodeMirror-rendered (<pre class="cm-content"><code>
    <span>...) but still a real pre>code pair with real newlines between
    token spans - .innerText reconstruction (same technique as Claude's
    adapter) produces clean, correctly-indented code, confirmed against a
    real generated Python function.
  - Real links render as plain <a href> (no flattening needed, unlike
    Claude's old PDF-link problem), but ChatGPT appends a "citation pill"
    chip after cited links (data-testid="webpage-citation-pill", wraps a
    tracking-decorated duplicate URL) which is stripped before Turndown
    runs, or its favicon+label text would leak into the export as noise.

Deliberately DEFERRED, not silently guessed at - each documented in the
file header with why:
  - Image embedding. Generated/uploaded images are same-origin
    chatgpt.com/backend-api/estuary/... URLs (promising - unlike Claude's
    unfetchable third-party web-search thumbnails, but untested). Web-
    search result images are cross-origin images.openai.com URLs, and one
    was confirmed to 404 with "Internal Server Error" when fetched outside
    the authenticated page context - likely the same unfetchable situation
    as Claude's web-search images, but not yet confirmed from inside an
    actual content script.
  - Canvas. The real trigger mechanism is still unconfirmed - a test
    prompt asking ChatGPT to open its native Canvas returned a plain-text
    "I can't open Canvas from here" response instead of doing so. What
    looked like Canvas during initial scoping turned out to be a
    third-party Canva app invocation (confirmed via api.canva.com network
    calls in the captured DOM), not ChatGPT's own feature - there is zero
    real DOM evidence for native Canvas yet.
  - Interrupted-response handling. No real DOM sample of a genuinely
    stopped ChatGPT response was captured during scoping - the one
    interrupt attempt was resent fresh rather than left stopped. Unlike
    Claude's confirmed data-is-streaming attribute, nothing here is
    confirmed, so no streaming-wait logic is implemented - deferring is
    safer than guessing at a selector the way earlier Claude sessions were
    burned by.
  - toolUses/artifacts arrays are always empty for the same reason: no
    real DOM confirmation yet for ChatGPT's own tool-use status widgets.

tests/helpers/dom-harness.js: parameterized to run either adapter (was
hardcoded to content.js/Claude only) via an optional scriptPath argument,
fully backward compatible - existing Claude tests don't pass it and are
unaffected. Also adds an innerText polyfill (returns textContent) since
jsdom implements no layout at all and therefore no innerText - a genuine,
pre-existing gap that turned out to affect content.js's own
extractCodeBlocks too (grep confirms tests/content.test.js has never once
exercised that code path against a real <pre> block) - not a new problem,
but a real one worth knowing about since it means the same jsdom gap could
have silently masked a real Claude code-block bug this whole time.

New tests/chatgpt-content.test.js: 7 tests, two using real markup pasted
directly from live DevTools inspection (a real cited link + its citation
pill, and a real CodeMirror-rendered Python function) rather than
simplified stand-ins, matching this project's established practice.

Test suite: 31 -> 38 passing tests.
